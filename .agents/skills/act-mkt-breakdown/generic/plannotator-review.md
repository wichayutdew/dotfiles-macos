# Plannotator review procedure

Read the latest canonical document and preserve user edits. Save the complete current artifact, not an outline or summary. Reuse its canonical local file when there is one; otherwise save a local Markdown review copy under the inherited `workspace.root` per [task directory](task-directory.md). Explicit user/AGENTS-required review locations take precedence. Persist the actual review path/version and decision in `.task-context.json`. Retain the canonical source/destination and the exact reviewed version in the continuation record. A local review copy does not authorize hosted publication. Include the review purpose described below in the document. Resolve any required input first, while continuing independent drafting/research. Do not submit unresolved tracker destinations as a creation proposal. Record the pending decision and continuation state, and state the exact actions approval would authorize.

Submit the artifact to Plannotator Inbox as an attachment with a `:::question` requesting explicit approval or feedback. Notify the user with the review reference and end the turn; do not poll, wait for the decision, launch a blocking CLI session, or open duplicate reviews. If Inbox is unavailable, report the blocker and provide the artifact path. Honor an explicit user choice of another review interface.

On a later response, reconcile the same artifact and review record. Explicit approval of the current artifact and scoped actions permits the next stage; carry approval notes forward without routine reconfirmation. On feedback, revise the same artifact, validate it, submit the revised version for review, notify the user, and end that turn. Dismissal, silence, elapsed time, a submission acknowledgment, failure, or approval of a materially different version is not approval. Reuse valid explicit approval without reopening the gate.

## Review purpose and next action

The complete proposal must include every epic/story, the source report version, the real tracker/workspace/team/project, supported object types, parent/child relationships, and selected metadata. Explicitly state that approval authorizes creating exactly these items in that destination. After approval of that creation proposal, immediately execute [create approved items](../workflows/create.md), read back the created items, and report verified links. Report acceptance or approval of content alone does not authorize creation. Material changes to content, destination, hierarchy, or metadata require renewed creation approval before affected writes.

# Stage: Publish

Publish only records and scope that passed Verify. Serialize mutations and use actual authenticated schemas in [memory-api.md](memory-api.md). Generated wording is acceptable; evidence, conditions and uncertainty must survive.

1. Reconcile before every first/retried write: exact top-level `oncall` folder, canonical feature tags/page/model IDs, confirmed source document IDs and pending operation IDs. Reuse remote objects after ambiguous calls; multiple matching targets block creation. Leave unrelated/historical pages untouched. Never move nodes to infer isolation.
2. Retain each contributing escalation as one complete document under `oncall:<rotation>:<esc_id>`, with oncall, rotation-id and every assigned feature tag. Use full replacement of that stable document, preserving all original rows/threads, literal URLs, dates, uncertainty and explicit corrections. Do not append duplicate events or make competing per-feature replacements. Metadata-only/no-contribution records remain accounted for in conversation; they create no visible archive or knowledge placeholder.
3. Wait for retention completion, then verify source facts are available in the strict page tag scope. Retention receipt, sync_retain completion or a pending consolidation job alone is insufficient. Recall world/experience/observation facts with original chunks, inspect document/source identity and use bounded retries. After timeout query recorded operations and reconcile source content before retrying. Pending source availability returns handoff, not a stale-page success.
4. Resolve/create only exact top-level `oncall` and direct feature children. For new features create the page with verified source query, strict tags and oncall parent. For existing pages preserve identities, update scoped query/settings only when needed, and refresh the backing model. Enable relevant consolidation refresh, all three fact types and original chunks. Size the budget to cover verified new and still-valid existing guidance; return content to Classify if meaningful feature subdivision is needed.
5. Wait for each generation operation's actual completion. Read exact page Markdown and folder tree; run the bundled check-page helper with literal required links, critical conditions/uncertainty terms, actual tags and actual/expected oncall parent. Independently compare meaning against verified drafts and earlier still-valid evidence. Check previously affected features after source corrections. Triage-only and unrelated feature guidance must not appear.
6. Content failure → Classify → Verify before corrective writes. If delta keeps deficient content, perform a verified full refresh with raw facts/chunks, then restore normal delta. Transient failures → handoff and reconcile/resume the same IDs; persistent ambiguity/access failure → blocked. Keep successful work and report pending generation separately; never infer success from a timeout.
7. Report affected page names/IDs, interval, distinct row/escalation coverage, complete unique threads, metadata-only/no-contribution outcomes, successful readbacks and failures in chat. Create no report, ledger, checkpoint or visible ticket archive. Empty/no-knowledge runs create no placeholder. Evaluate representative recurring oncall questions when introducing or materially changing the taxonomy; generation success alone is not retrieval-quality proof.

`ready`: every scoped write and affected readback confirmed, or verified no-write result reported. `content`, `handoff` and `blocked` follow the routes above.

# Stage: Publish

Use only the records and feature scope that passed Verify. Serialize remote mutations. Follow [memory-api.md](memory-api.md); inspect actual authenticated schemas and preserve returned IDs. Generated wording may differ, but no source-backed finding, citation, condition or uncertainty may disappear or change meaning.

1. Reconcile remote state before the first write and every retry: exact top-level `triage` folder ID, page identities, prior confirmed retention results and pending operation IDs. Reuse an existing folder/page rather than assuming an interrupted call failed. Multiple ambiguous matching targets are `blocked`, not permission to create another. Do not migrate historical profile subfolders or touch unrelated nodes. Reuse feature pages across relevant profiles in this bank.
2. Retain the complete verified evidence for each ticket under its stable profile/channel/thread document identity, with the profile and every assigned feature tag. Replace that full document using the supported schema; do not append the same event repeatedly or write competing per-feature replacements. Include source links, source dates/revision and explicit corrections in the retained content. Preserve earlier still-valid knowledge. Wait for retention operations to complete. After timeout, query the recorded operation and reconcile the stable document's retained facts/content through supported read tools before retrying; operation acceptance alone is not retention or consolidation completion.
3. Wait for the new evidence to be available in the page's configured source scope. Pages use consolidated observations by default, so successful `retain` or `sync_retain` alone is insufficient. Use supported observation recall/status evidence and bounded retries. If consolidation is pending, report `handoff` with confirmed retention and pending page work; do not generate an apparently complete page from old facts.
4. Resolve/create only the exact top-level `triage` folder. For a new feature, call `create_knowledge_page` with its verified name, scoped source query, strict tags and triage-folder parent. For an existing feature, preserve its identity, update only the approved query/tags/settings when needed and call `refresh_mental_model` for its backing model. Enable relevant consolidation refresh with raw source facts plus observations and original-chunk retrieval so citations and caveats survive synthesis. Use the settings in memory-api.md. Size the content budget to retain all relevant verified guidance; if a page becomes too broad, return `content` to Classify for meaningful feature subdivision rather than silently truncating it.
5. Wait for every page-generation operation to complete; failed or pending operations are not published pages. Read back the exact page and folder tree. Confirm parent folder, triage/feature scope, all six sections, required source links and critical facts/conditions/uncertainty. Run the bundled `check-page` helper using Markdown, required source links/terms, actual page tags and actual/expected triage parent IDs; independently compare meaning to the verified drafts and existing still-valid citations/conditions. Inspect previously affected feature pages too when assignments/corrections changed. Unrelated curator or feature content must not appear. Profile provenance must survive when several profiles contribute.
6. A content/readback failure returns `content` → Classify → Verify before corrective writes; preserve already confirmed valid work. After corrective classification/verification, use a full rebuild if delta preserves the deficient content; verify it and restore normal delta mode afterward. Transient failures return `handoff` and resume the same identities/operations. Persistent missing access or ambiguous writes return `blocked` with exact completed and remaining actions. Never infer success from a timeout or an ingestion receipt.
7. Finish with affected page names/IDs, interval, selected/evidenced/no-contribution ticket counts, successful readbacks and specific limitations. Keep it in chat; create no report, ledger, index or checkpoint file. Empty/no-reusable-knowledge runs create no placeholder page.

`ready`: every scoped write is confirmed and every affected page passes readback, or a verified no-write run is reported. A successful page generation does not prove retrieval quality; use representative support questions when evaluating a new or materially changed feature taxonomy.

# Stage: Classify

Use the complete collection, thread evidence and existing triage feature pages. Produce feature drafts in conversation; mutate nothing.

1. Extract one ticket evidence record per selected source identity: profile, channel, root timestamp, Slack URL, opening, completion (`done_at`) and incident/verification dates, source revision or latest observed update, symptoms, actions, confirmed findings, applicability conditions, ownership and unresolved questions. Separate confirmed facts, corroborated evidence and unconfirmed hypotheses. Attribute an assertion to a human or automation only when its source establishes that origin; otherwise leave origin unspecified. Preserve the exact source-backed action and conditions without inventing operational alternatives, prerequisites or diagnostic ordering. Preserve contradictions and evidence that could falsify a finding.
2. Search/read existing pages directly within the exact top-level `triage` folder and matching triage/feature memory scope before assigning a feature. Reuse their canonical feature slug, title and IDs. Folder placement alone does not scope memory. Two tickets about campaign reapproval should enrich one feature page; a ticket spanning feed eligibility and POI mapping can contribute to both. Create a new kebab-case feature slug only for a genuinely distinct troubleshooting topic. Feature pages may combine relevant profiles in this authenticated team bank. Do not match solely on a similar title or include another curator namespace's sources.
3. Reconcile current ticket facts with existing retained knowledge. Preserve still-valid conditions and earlier incident history. Explicitly mark corrections and what they supersede, citing newer evidence; an old incident's verified resolution stays historical, not a guarantee of current behavior. Preserve unverified competing explanations under Unresolved questions. Never translate a closed support status into a confirmed fix.
4. Draft each affected page using the six headings in SKILL.md. Symptoms include alternative user terms; Diagnosis gives source-backed distinguishing checks; Known resolutions states prerequisites and limitations. Evidence cites ticket/Jira links and dates. Empty sections state the missing evidence. Integrate duplicate guidance while keeping all supporting sources.
5. Account for every selected ticket in conversation: its source identity, assigned feature(s), contribution or evidence-backed reason it adds no reusable knowledge. A ticket without reusable knowledge need not create a page, but it is not silently skipped or counted as published knowledge. If existing feature assignments change, refresh all affected old and new pages after the source correction; do not leave stale guidance on the previous feature.
6. Prepare stable document identities and tags using [memory-api.md](memory-api.md) and the bundled helper. Each retained ticket includes all feature assignments, not one conflicting replacement per feature. For each feature carry required source links, critical identifiers/conditions/uncertainty terms for readback, existing IDs or new-page intention and the complete grounded draft. These are proposed scoped writes, not a human approval artifact.

`ready`: all selected tickets are accounted for and every proposed feature has evidence-backed scope and a complete draft. `gaps`: required sources/counts are incomplete → Collect. `handoff`: classification remains unfinished. `blocked`: unsafe disclosure, irreconcilable source identity or unavailable evidence prevents safe knowledge publication. No reusable knowledge is a valid no-write result with the reason reported.
